# MET Norway Forecast Provider Contract

- **Provider:** MET Norway Locationforecast/2.0, served by the Norwegian Meteorological Institute through the MET Weather API.
- **Purpose:** Active installed-app forecast fallback provider for current conditions, hourly forecast, daily forecast, Home metric/source/provenance display, stale/cache metadata, and provider-neutral fallback selection after eligible Open-Meteo terminal forecast failures. Fixture parsing, DTO/client/mapper/repository work, cache metadata persistence, fallback selection, attribution disclosure, and installed-boundary fallback verification are implemented; conditional GET/304 handling, provider health/backoff, and release-candidate fallback verification remain later work.
- **Coverage:** Global point forecast coverage for any latitude/longitude accepted by Locationforecast. MET Norway documents Nordic and Arctic regions as the main priority with more frequent and accurate short-range forecasts, and the rest of the world as ECMWF-based global forecasts. Forecast horizon is short- to medium-range, up to about nine or ten days depending on documentation page, model region, and available timesteps. Field availability varies by geography, forecast range, and aggregation period; missing provider values remain null/unknown in Oxygen.
- **Base endpoint:** `https://api.met.no/weatherapi/locationforecast/2.0/compact?lat={latitude}&lon={longitude}` with optional `altitude={wholeMeters}` when Oxygen has trusted elevation for the selected `WeatherLocation`. Use `compact` JSON/GeoJSON for the MVP Home path. Keep the base URL and request construction isolated from UI code. Do not use the legacy XML `classic` method for new Oxygen code.
- **Authentication:** No API key, account, SDK, OAuth flow, or paid subscription is required for the public Locationforecast API. Requests must still identify Oxygen through HTTP headers as required by MET Norway terms.
- **Required headers:** Every production request must send a unique, identifying `User-Agent` value containing the application/domain name and a contact channel, for example `OxygenWeather/<version> <project-or-contact-url>`. Generic Android, Java, OkHttp, Dalvik, blank, browser-mimicking, or missing user agents are invalid for Oxygen. Future clients should request JSON with `Accept: application/json` and must support conditional GET with `If-Modified-Since` when cached `Last-Modified` metadata exists.
- **Request/rate limits:** MET Norway does not publish a simple fixed public numeric quota for Locationforecast in the reviewed docs. Its terms require clients to avoid unnecessary traffic, not repeat requests until the `Expires` response time, cache locally, use `If-Modified-Since`, avoid HEAD-then-GET patterns, and spread scheduled requests over time instead of aligning them exactly on model-update boundaries. Requests should send coordinates with no more than four decimals to support provider caching and avoid blocking. Future repository refresh logic must apply jitter/backoff and must not retry MET Norway from every recomposition or location switch.
- **Caching rules:** HTTP cache guidance is provider-specific and takes precedence where appropriate. Persist at least response `Expires`, `Last-Modified`, `ETag` if present, fetch time, response coordinates/elevation, provider `meta.updated_at`, and provider ID with cached forecast data. Do not request again before `Expires` unless the user explicitly refreshes and the repository policy permits it. Use `If-Modified-Since` for revalidation when `Last-Modified` is known. Treat HTTP 304/not-modified as cache-not-modified and keep the existing cached forecast with refreshed cache metadata. If provider cache headers are missing or unusable, fall back to Oxygen's cache policy targets: current about 15 minutes foreground refresh with about 2 hours stale tolerance, hourly about 30 minutes refresh with about 6 hours stale tolerance, and daily about 2 hours refresh with about 24 hours stale tolerance. UI/cache consumers receive only provider-neutral freshness/provenance state, not raw MET Norway headers.
- **Fields used:** Request one Locationforecast compact response for a single explicit `WeatherLocation` with WGS84 latitude/longitude and optional whole-meter altitude. Oxygen must derive Home current, hourly, daily, metric, source/update, provenance, stale, and cache needs from the GeoJSON `properties.meta` and `properties.timeseries` envelope.

  Required envelope and metadata:
  `type`, `geometry.coordinates` as longitude/latitude/altitude, `properties.meta.updated_at`, `properties.meta.units`, and sorted `properties.timeseries`.

  Current and hourly source fields:
  `timeseries[].time`; `data.instant.details.air_temperature`; `air_pressure_at_sea_level`; `cloud_area_fraction`; `cloud_area_fraction_high`; `cloud_area_fraction_medium`; `cloud_area_fraction_low`; `dew_point_temperature`; `fog_area_fraction` where available; `relative_humidity`; `ultraviolet_index_clear_sky` where available; `wind_from_direction`; `wind_speed`; `wind_speed_of_gust` where available; `data.next_1_hours.summary.symbol_code`; `data.next_1_hours.details.precipitation_amount`; `precipitation_amount_min`; `precipitation_amount_max`; `probability_of_precipitation`; and `probability_of_thunder`.

  Daily source fields:
  Build daily rows from available `timeseries` instants and period aggregations for the selected location timezone. Use `next_6_hours` and `next_12_hours` period summaries/details when `next_1_hours` is no longer available, including `summary.symbol_code`, `air_temperature_min`, `air_temperature_max`, `precipitation_amount`, `precipitation_amount_min`, `precipitation_amount_max`, `probability_of_precipitation`, `probability_of_thunder`, and `ultraviolet_index_clear_sky_max` where present. If a future daily UI requirement needs sunrise/sunset or daylight duration, those values must come from another contracted source or a clearly marked local astronomical calculation; Locationforecast compact does not provide sunrise/sunset fields.

  Apparent temperature is not a direct Locationforecast field in the reviewed compact documentation. Future Oxygen code may omit apparent temperature for MET Norway or derive it from contracted temperature, humidity, and wind fields only if the derived provenance remains clear and missing inputs produce null, not fabricated values.
- **Time format:** Locationforecast timestamps are ISO 8601 UTC values such as `YYYY-MM-DDThh:mm:ssZ`. Provider timestamps enter Oxygen domain as `Instant`. `WeatherLocation` owns the IANA `ZoneId`; presentation converts instants to the selected location's local clock. Do not interpret a remote forecast with the phone timezone. `properties.meta.updated_at` is provider issue/update metadata and should map to provenance `issuedAt` when valid. `fetchedAt` is the client fetch time.
- **Unit format:** Use provider units from `properties.meta.units` and validate them during parsing. Contracted canonical mappings are: Celsius for `air_temperature`, `air_temperature_min`, `air_temperature_max`, and `dew_point_temperature`; hPa for `air_pressure_at_sea_level`; percent for cloud, fog, humidity, and precipitation/thunder probabilities; millimeters for precipitation amounts; degrees clockwise from north for `wind_from_direction`; meters per second for `wind_speed` and `wind_speed_of_gust`; and unitless UV index for UV fields. Oxygen stores canonical domain values and converts only for presentation. If a response declares an unexpected unit for a required mapped field, classify it as an invalid response for that field/path rather than silently converting by assumption. Missing/null provider values remain null/unknown, never zero.
- **Weather-code mapping:** Locationforecast uses string `symbol_code` values in period `summary` objects. The filename stem in the MET weathericons repository corresponds to `symbol_code`, including `_day`, `_night`, and `_polartwilight` variants. Future mapper code must normalize only the day/night/polartwilight suffix for condition mapping; it must not leak symbol strings into Composables, Home state, saved locations, unit presentation, or cache consumers.

  Contracted symbol families:
  - `clearsky_*` -> `CLEAR`
  - `fair_*` -> `MOSTLY_CLEAR`
  - `partlycloudy_*` -> `PARTLY_CLOUDY`
  - `cloudy` -> `CLOUDY`
  - `fog` -> `FOG`
  - `lightrain`, `lightrainshowers_*`, and matching `light...rain...andthunder` families -> `DRIZZLE` or `THUNDERSTORM` when thunder is explicit and no stronger rain category is selected by the mapper policy
  - `rain`, `heavyrain`, `rainshowers_*`, `heavyrainshowers_*`, and matching rain/thunder families -> `RAIN`, `RAIN_SHOWERS`, or `THUNDERSTORM`
  - `sleet`, `heavysleet`, `sleetshowers_*`, `heavysleetshowers_*`, and matching sleet/thunder families -> `SLEET` or `THUNDERSTORM`
  - `snow`, `heavysnow`, `snowshowers_*`, `heavysnowshowers_*`, and matching snow/thunder families -> `SNOW`, `SNOW_SHOWERS`, or `THUNDERSTORM`
  - any documented symbol family containing thunder and hail if introduced later -> `THUNDERSTORM_HAIL` or `HAIL` according to the explicit symbol semantics
  - the documented typo families `lightssleetshowersandthunder_*` and `lightssnowshowersandthunder_*` must be accepted if present
  - any unknown, unsupported, malformed, empty, or null `symbol_code` -> `UNKNOWN`

  The future Slice 13B mapper must include fixture-backed tests over the complete official symbol-family list current at implementation time. The contract does not add icon assets or UI icon behavior.
- **Error responses:** MET Weather API errors may be plain text or HTML depending on request headers. Future client code must classify from HTTP status and `X-ErrorClass` where present. Required Oxygen classifications: network/offline; rate limited from HTTP 429 or `X-ErrorClass: Ratelimitation`; provider unavailable from HTTP 500/502/503 or backend/internal error classes; invalid response/request from malformed body, invalid schema, invalid required fields, invalid units, HTTP 400 parameter/format/validation classes, missing required envelope, or unexpected body shape; unsupported or insufficient forecast data from outside-geographic-area, no-data, outside-time-range, no usable Home-path timesteps, or absent required current/hourly data; cache-not-modified from HTTP 304; and illegal identification from HTTP 403 or `X-ErrorClass: IllegalUserAgent`, which is a client configuration failure. Provider-specific status text, HTML bodies, and `X-ErrorClass` values must stay in provider diagnostics and must not cross into UI state as provider-specific copy.
- **Attribution:** Display MET Norway attribution anywhere MET Norway forecast data is displayed. Acceptable copy should be equivalent to `Data from MET Norway` or `Based on data from MET Norway`, with a link to the MET Weather API or source page where the data can be downloaded. Attribution must not imply MET Norway endorses Oxygen.
- **License:** Unless otherwise specified by a product, MET Norway data and products are licensed under the Norwegian Licence for Open Government Data (NLOD) 2.0 and Creative Commons Attribution 4.0 International (CC BY 4.0). Weather icon assets are separately licensed under MIT by Yr.no; this slice does not import those icon assets.
- **Privacy implications:** Forecast requests to MET Norway send selected location coordinates, optional altitude, request headers including Oxygen's identifying User-Agent/contact string, and normal network metadata such as IP address. MET Norway terms state that direct app/browser API calls reveal user IP addresses and possible geocoordinates in logs, and recommend a proxy gateway to guarantee anonymity. The reviewed privacy statement says IP addresses for meteorological data websites without login are stored for up to 90 days and can be used for service capacity, abuse detection, operational issues, and traffic management. Oxygen must disclose these facts before presenting MET Norway as an active fallback. Manual location support must remain fully functional without Android location permission.
- **Failover behavior:** Open-Meteo remains the default MVP forecast provider. MET Norway is the active installed-app forecast fallback after eligible Open-Meteo terminal forecast failures through the selected-location Home refresh path. Fallback selection must never average, merge, smooth, blend, or mix MET Norway values with Open-Meteo values. A displayed forecast bundle comes from one serving provider at a time, and provenance must identify that provider. Open-Meteo success, offline/network failure, and provider-rejected requests must not call MET Norway. MET Norway fallback success must keep MET Norway attribution, license, source/update, stale/cache metadata, and provider ID. Forecast provider fallback must not disable official alert lookup.
- **Fixture/sample response location:** Parser fixtures live under `core/src/test/resources/providers/metno/` unless the provider implementation is moved to another testable module. The implemented fixture set covers normal compact Home forecast response, missing optional fields, malformed envelope, unexpected units, unknown symbol code, documented typo symbol code, and timezone-sensitive UTC response. Later conditional GET/304 and provider error-class slices must add fixtures for 304/cache-not-modified metadata, rate/error response with `X-ErrorClass`, and illegal/generic User-Agent response as needed.

## Oxygen Semantics

Locationforecast values are automatic forecast/model values. Oxygen must represent MET Norway current-condition values as `DataType.MODEL_ESTIMATE` when shown as current conditions, and hourly/daily rows as `DataType.FORECAST`, unless a later provider review identifies a documented observation source for a specific value.

Provider DTOs, symbol codes, endpoint parameters, response headers, `X-ErrorClass` values, provider cache directives, and product names remain provider implementation details. Repository, cache, and UI consumers may receive only provider-neutral Oxygen models, provenance, freshness/stale state, and errors.
